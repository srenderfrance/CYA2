# Production review and consolidated backlog

Review date: **2026-11-04**. This is the authoritative current backlog; the older TODO documents retain implementation history and link here. Application code was not changed during this review.

## Soft-credit identity follow-up

Donation uploads now require the `Soft Credit Recipient ID` column; eligible third-party soft credits use that ID, with existing name fallback for blank values. Equal direct and soft-recipient IDs are treated as the same person by user decision; confirm their shared namespace with the source provider before real data. The initial schema and rollback snapshots contain the new column; previously initialized Azure and Aiven test databases need explicit alignment or recreation before this version is used. Intern identity is unchanged. See [import safety](IMPORT_SAFETY.md).

## Audit reliability follow-up

- **A10:** required success evidence is now in the same transaction as supported user/bootstrap/import/rollback mutations. Imports require durable starts and share their generated progress/operation ID through queued work. Export completion is recorded after workbook generation and required before returning bytes. Unknown, partial and cancelled outcomes are distinct; prior-process unfinished imports are flagged without replay. See [audit operations](AUDIT_OPERATIONS.md) for the evidence limits, single-process assumption and reconciliation procedure.
- **B09:** independent sanitized monitoring events 9100–9103 are implemented. The selected delivery is **monitoring logs only for now**; no external alert rule, email or webhook is configured or verified. Deployed sink/retention and operator response remain acceptance gates.
- Initial schema includes correlation/target fields and retains numeric actor history after user deletion. Existing databases have not been aligned; required writes fail closed against an old audit schema. Explicit safe schema alignment is required before deployment, not an automatic reset.
- Local unit/Web and disposable MySQL coverage does not prove process-kill recovery, lost commit acknowledgements, browser receipt, or deployed monitoring. The in-memory queue is not durable and cache/progress delivery remains post-commit.
- Final local validation: solution build succeeded; Application **225/225**, Web **77/77**, and enabled database project **53/53** passed, with zero skipped and captured exit codes 0. No disposable test container remained. Existing unrelated nullable warnings remain outside this audit scope.

## User-administration follow-up

- **A12:** user creation, profile/access changes, intern account handling, and deletion use one serialized MySQL transaction per operation. The store rechecks the actor's current Admin role, blocks self-deletion and self-demotion, and protects the last Admin. Staff edits submit profile and access changes together. Duplicate email and intern-account reuse return safe, specific outcomes. Google binding and language updates no longer overwrite full user rows.
- Focused application regressions and eight disposable-MySQL lifecycle tests passed, including concurrent administrator deletions, duplicate-email races, injected transaction failures, intern typo/reuse, and stale-profile protection. The full database runner reported 48/48 passed; its terminal wrapper later reported cancellation without an exit code, and no disposable container remained. These are local results, not deployed-Azure or browser acceptance. An unconfirmed database outcome causes conservative cache invalidation and instructs the operator to refresh and verify before retrying; actual lost-commit acknowledgements remain untested.
- **Release clarification:** the user reports the existing GitHub workflow targets a separate development Azure deployment, not the current production/test environment, which is published directly from Visual Studio. The workflow redesign is deferred until the correct GitHub account is connected; it remains a launch gate, not evidence that the present deployment is automatically updated.

## Executive assessment

**Not ready for real donor/financial data yet.** The app has substantial protections and passing tests, but source inspection identifies import recovery, contact freshness, donor reporting and session/diagnostic gaps. Production-environment acceptance has not been demonstrated. A passing build is not a launch approval.

Use three stages below: **A — work possible now**, **B — deploy privately and verify before going live**, **C — ongoing improvements**. An item in A or B marked **Gate** must be resolved or have an explicit, time-limited owner-approved exception before launch; financial integrity/privacy failures should not be deferred merely because the user count is small. Other improvements can be scheduled with a named owner. The sole maintainer can approve releases: no required PRs or second-person production approval are assumed.

Evidence labels:
- **Confirmed:** directly supported by current source; not necessarily runtime-reproduced.
- **Verify:** credible concern or deployment condition requiring a targeted test.
- **Implemented:** source/test coverage exists, with environment acceptance separately tracked.
